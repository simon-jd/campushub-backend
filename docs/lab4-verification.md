## Decisions Resolving Assignment Ambiguities

Two readings of the brief led to materially different work, so both were put to the student before
any code was written, and both were answered by the student.

- **"List all bookings" (Part 2).** The Lab 3 listing returned only non-cancelled reservations
  ending in the future, so a cancelled booking vanished instead of showing as `CANCELLED` — which
  would have made Part 1's state-management rule unobservable through the API. The student chose to
  widen the default to every reservation the user owns and add an optional `status` filter. This is
  a deliberate breaking change: contract 1.2.0 documents it, and the one Lab 2 regression assertion
  that encoded the old behavior was updated to assert the new one. Creation order (`_id`) is
  unchanged.
- **Confirm endpoint (Part 1 vs Part 2).** Part 1 names transitions to both `CONFIRMED` and
  `CANCELLED`; Part 2's deliverable list names only cancel. Since `POST /reservations` creates
  `CONFIRMED` reservations, a confirm route would have had nothing to act on and would have been
  dead code. The student chose to wire both routes over one shared transition function and to seed a
  `PENDING` reservation so confirm is genuinely reachable and demoable.

Decisions made without consulting the student, as routine engineering judgment:

- **Re-applying a status is a conflict, not a no-op.** `CANCELLED` is terminal and no status is a
  legal source for a transition to itself, so cancelling a cancelled reservation returns
  `409 INVALID_STATE_TRANSITION`. This is distinguishable from `404`, which a silent idempotent
  `200` would not be.
- **A malformed `id` returns 404, not 400.** This matches how creation already treats a `resourceId`
  that cannot be an ObjectId (Lab 2's `res-101` returns `404`), so the two routes stay consistent.
- **Transitions are one conditional update.** `findOneAndUpdate` filters on both `_id` and the
  permitted source statuses, so two concurrent cancellations cannot both observe the same source
  status and both report success. A second read then separates "no such reservation" from "status
  forbids this transition". A cancellation needs no booking lock: it only removes an interval from
  the overlap query, so a create racing it either still sees the reservation and declines, or no
  longer sees it and succeeds. Neither outcome double-books.

## Context Rule Changes (AGENTS.md)

`AGENTS.md` §1 requires the reason and impact of rule changes. No compiler setting, lint severity,
or ignore entry was relaxed, and no suppression was added anywhere in this lab.

1. "the three required resources/reservations endpoints" → "every resources/reservations endpoint
   (Lab 2's three, plus the Lab 4 status transitions)". Reason: two endpoints were added. Impact:
   none beyond scope of the existing layering rule.
2. Added the half-open overlap sentence "Cancelling releases an interval immediately, so the slot
   becomes bookable again." Reason: Part 1's state-management rule. Impact: documents behavior the
   tests now enforce.
3. Added a reservation state-machine rule (terminal `CANCELLED`, no self-transition, one conditional
   update, `409` distinct from `404`). Reason: new behavior that would otherwise be undocumented and
   easy to regress into a read-modify-write. Stricter, not looser.
4. "The Lab 2 HTTP suite is the regression suite" → "The Lab 2 and Lab 4 HTTP suites". Added a rule
   that both suites assert against `docs/openapi.json` via `src/tests/contract.helper.ts`. Reason:
   the new suite carries equal regression weight. Stricter, not looser.
5. Test database naming widened to "per-suite, per-process" to cover `campushub_lab4_<pid>`.

## Diagnostics and Corrections

Three agent failures occurred during Part 2 and are documented in
[lab4-steering-log.md](lab4-steering-log.md): a hallucinated `FilterQuery` import that does not
exist in Mongoose 9; a seed helper copied from `seedResources` into a schema whose cross-field
validator cannot run under update validators; and a generated comment that contradicted the
assertion directly beneath it. All three were caught by mechanical gates — `tsc`, a deliberate
throwaway probe, and the test runner — rather than by rereading the generated code.

**No student-authored prompt was issued mid-loop for any of the three.** The agent self-corrected
under standing rules already committed in `AGENTS.md` §7, which forbid the `any` / `@ts-ignore` /
`eslint-disable` repairs an agent reaches for when an error proves stubborn. The steering log states
this explicitly, separates what actually intervened from the reactive prompts that were written
during the retrospective and never sent, and labels the latter as unused. Incident 1 was re-staged
afterward — the hallucinated import reintroduced and `npm run typecheck` re-run — to confirm its
error text is reproducible rather than recalled.

## Limitations

- The Part 3 human audit of `AGENTS.md` and the generated code has not been performed. The agent's
  checks do not substitute for it.
- Booking serialization remains single-process, as in Lab 3. Several server processes sharing one
  database could still interleave an overlap check and an insert. Status transitions do not share
  this limitation: each is a single conditional update and is therefore safe across processes.
- `GET /reservations/user/{userId}` accepts any syntactically valid identifier; there is still no
  user database or authentication, so one student can read another's reservations.
- The user listing is unpaginated. Now that it returns cancelled and elapsed reservations as well,
  it grows without bound for an active user.
- The contract is validated structurally by both HTTP suites against the responses we actually
  return; it has not been re-run through an external OpenAPI linter for this lab.
