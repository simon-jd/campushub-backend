## Decisions Resolving Assignment Ambiguities

- **ObjectId identity.** The lab requires `Reservation.resourceId` to be an ObjectId reference to `Resource`, so MongoDB `_id` (hex) is now the API `id` for resources and reservations. The contract adds an `ObjectId` schema; `Reservation.id` changes from UUID to ObjectId (contract version 1.1.0). Services map documents to the API types; Controllers never see Mongoose documents.
- **No 404 regression.** `CreateReservationRequest.resourceId` still accepts any Lab 2 identifier. Values that cannot be ObjectIds (for example `res-101`) match no resource and keep returning `404 RESOURCE_NOT_FOUND` instead of becoming `400`.
- **Stable sample IDs.** `npm run seed` upserts the Lab 2 catalog with fixed ObjectIds `…0101` to `…0104`, so manual curl requests stay copyable and reseeding never orphans reservations.
- **Times are BSON dates.** Overlap is a database query on `[startTime, endTime)` instants; responses are normalized back to UTC ISO strings exactly as in Lab 2.
- **Concurrency.** Lab 2's guarantee (five simultaneous identical bookings produce exactly one `201`) depended on synchronous check-and-insert. With two awaited round trips it would regress, and standalone MongoDB has no multi-document transactions. `reservation.service.ts` therefore serializes bookings per resource inside one process. This is documented as not protecting multiple processes.
- **Test isolation.** The HTTP suite connects to the configured MongoDB server but uses a throwaway `campushub_test_<pid>` database, seeds its own fixtures, and drops it afterward. `npm test` now loads `.env` (like `dev`/`start`) so it targets the same server.

## Controllers and Services Review — 2026-10-05

This was a focused AI review requested by the user. It does not replace or record the Lab 3
student-only human audit. The reviewed files were all files under `src/controllers/` and
`src/services/`, with their routes, types, validation functions, Mongoose models, OpenAPI responses,
and HTTP tests read as supporting context. No Controller or Service source files were changed.

**Result: no correctness, response-contract, or layer-boundary findings were identified in the
reviewed scope.**

### Controller review

- `health.controller.ts` calls the synchronous Health Service and returns the direct `HealthResponse`
  with status `200`. It contains no database access or unnecessary Health abstractions.
- `resource.controller.ts` accepts only the documented `type` query, normalizes the assignment alias
  `STUDY_ROOM` to `ROOM`, rejects unknown or invalid query values with the shared `{ code, message }`
  error shape, and delegates the read to `listResources`.
- `reservation.controller.ts` validates media type, body shape, query parameters, path identifiers,
  and interval input before calling a Service. It maps the `ReservationResult` discriminated union to
  the documented `201`, `404`, and `409` responses and returns direct domain objects or arrays. It
  contains no Mongoose imports, Model calls, persistence logic, or duplicated overlap rules.
- The async Controllers do not catch and rewrite unexpected failures. Their rejected Promises reach
  the shared Express 5 error middleware, which preserves the generic `500 INTERNAL_ERROR` contract.

### Service review

- `resource.service.ts` is the only host for Resource Model reads and seed upserts. It validates
  ObjectId compatibility before `findById`, maps Mongoose documents to plain `Resource` values, and
  does not expose Mongoose documents to Controllers.
- `reservation.service.ts` owns the resource lookup, availability rule, half-open overlap query,
  reservation insert, active-reservation query, and document-to-domain mapping. The overlap query
  correctly blocks non-cancelled records where `existing.startTime < requested.endTime` and
  `existing.endTime > requested.startTime`, while allowing adjacent intervals.
- The per-resource Promise queue orders the overlap check and insert within one Node process, forwards
  failures to the caller, and removes an idle queue entry in `finally`. Its multi-process limitation is
  explicitly documented and remains a known limitation rather than an unreported guarantee.
- `health.service.ts` returns only a fresh plain status object and remains independent of MongoDB.
- Services import no Express request/response types, set no HTTP status codes, and construct no HTTP
  response envelopes. All observed Mongoose reads and writes in application code remain in Services.

## Limitations

Bookings are serialized per resource within one process only. There is no authentication, user lookup, or cancellation endpoint. Unique-index and cross-document guarantees beyond the overlap query are not claimed. Automated or agent review is not human approval.
